# Release 0.1 — Foundations: delivery plan

Read first: `CLAUDE.md`, `CONTRIBUTING.md`, `SPEC.md`, `docs/architecture.md`. Work on the branch `release/0.1`.

Each delivery below is one patch version. A delivery is done when its acceptance criteria hold and the Definition of Done in `CONTRIBUTING.md` is met. That includes:

- adding the delivery to `CHANGELOG.md`;
- ticking it in this file;
- bumping `version` in `package.json`.

Do the deliveries in order; each one builds on the previous. If something here is unclear or looks wrong, stop and ask. Do not guess, because these are contracts.

**Release exit criteria** (from `ROADMAP.md`):

- domain and rules tests pass in CI;
- the start page opens on a phone over HTTPS.

## [x] 0.1.3 — Randomness and ids

Create `src/core/random.ts`. `src/core/` cannot touch `crypto`, so the source of random bits is passed in.

```ts
export type FillRandom = (array: Uint32Array) => void;   // production: (a) => crypto.getRandomValues(a)
export function createRandomInt(fill: FillRandom): RandomInt;   // RandomInt = (maxExclusive: number) => number
export function randomWorldId(randomInt: RandomInt): WorldId;   // 28 chars, [A-Za-z0-9]
```

Add `export type RandomInt = (maxExclusive: number) => number;` and `export type Clock = () => Millis;` to `src/core/model.ts`.

Acceptance:

1. **No modulo bias.** `createRandomInt` uses rejection sampling. Test it with a scripted `fill` that first returns a value in the rejected zone (for `maxExclusive = 3`, `0xFFFFFFFF`), then an accepted one, and check that the rejected value is skipped.
2. **Range.** `maxExclusive` must be an integer from 1 to 2³²; anything else throws `RangeError`.
3. **Distribution.** 30,000 draws of `randomInt(3)` with the real `crypto.getRandomValues` fall within 33.3% ± 1.5% each.
4. **World ids.** `randomWorldId` returns 28 characters, all in the alphabet. 1,000 ids are all distinct.

## [x] 0.1.4 — Memory adapter and contract tests

Create:

- `src/data/memory/` with `createMemoryBackend()` and `createMemoryStore(backend, { uid, clock, randomInt })`, as described in `docs/architecture.md` §5;
- `src/data/datastore.contract.ts`, exporting `runDataStoreContract(name, makeDevices)`. Here `makeDevices()` returns fresh, connected stores for several devices (`admin`, `child`, ...) sharing one backend;
- `src/data/memory/memory.test.ts`, running the contract against the memory adapter.

The contract suite must include at least the cases below. Every rejection is checked on `settled` with the exact `DataStoreError.code`.

| Area | Case |
| --- | --- |
| World | `createWorld` gives an id of 24 or more characters. `observeWorld` emits the name, `themeId` and `DEFAULT_RULESET`. The creator's adult profile exists, and the creator's membership has it as `profileId`, so the creator is admin at once |
| Join | A second device joins with `profileId: null`. Joining again is a no-op. Joining an unknown id rejects with `not-found` |
| Profiles | An admin creates a profile and every device's `observeProfiles` emits it. A device on a child profile creating one rejects with `permission-denied`. Archiving a child profile keeps it, with `archived: true`. Archiving an adult profile rejects with `permission-denied` |
| Profile choice | `chooseProfile` updates the membership. Choosing an archived profile rejects with `permission-denied`. Switching later works |
| Admin rights | A device on a child profile cannot do admin operations. After `chooseProfile` to an adult profile, it can. A device without a profile cannot |
| Ad hoc tasks | An admin creates one for any profile, with `createdBy` = the admin's active profile. A child creates one for itself; for someone else it rejects with `permission-denied`. A device without a profile rejects with `permission-denied` |
| Observing | `observeOpenTasks` lists only open tasks of that profile, oldest first, and updates when one is completed. The first emission happens without any write |
| Completing | The owner completes: `status: done`, `doneAt` = clock, `weekKey` = `weekKey(clock(), ruleset.timezone)`. A task with a question needs `answer: 'yes'`, otherwise `invalid-argument` before any write. An admin completing a child's task rejects with `permission-denied`. Completing the same task on two devices (same profile): the first is accepted, the second rejects, and both devices end up showing `done` |
| Talk flag | The owner sets and clears it on an open task. On a done task it rejects |
| No false state | After any rejection above, the observers of every device show the backend's state |
