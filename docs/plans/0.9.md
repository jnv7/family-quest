## A. The rules every delivery keeps

These are the product and engineering rules that 0.9 touches. Each delivery's acceptance checks them.

| # | Rule | How 0.9 keeps it |
| --- | --- | --- |
| R1 | **A theme is a skin** (ADR 0006) | The token's name and icon, the depth of the `vault`, and the invitation texts are theme data. Code says `token`, `tier` and `vault`. There is no `if theme === …`, and `lint:theme-leak` gains `tocha`, `tochas`, `torch` and `torches` |
| R2 | **Local-first** | Earning and spending are `writeBatch` with `increment()`, with no transaction and no read from the server first. Opening works offline |
| R3 | **No double spending** | The rules check every balance change against its reason, and never let it go below 0 (ADR 0008 §2) |
| R4 | **Nothing earned is deleted** | Tokens are a counter whose every change has a stored reason (a done task's `tokens`, a reward's `price`). No document is deleted. A rejected purchase spends nothing |
| R5 | **A done task never reopens** | The rules check amounts by range, not against the `ruleset`, and keep the 0.8 completion path (ADR 0008 §5 and §6) |
| R6 | **No counts, except your own balance** | The number appears only at the top of the `vault`, for the active profile. It never appears on the map, the card or any other screen, nor in the adults' view. `Profile` does not carry it |
| R7 | **No friction** | Completing a task stays at 2 taps (3 with a question). Opening takes 2 taps: choose, then "open for N" |
| R8 | **Each person only their own** | Only the owner earns or spends. An admin never touches a balance |
| R9 | **Text in locale files** | Every new string goes in `pt-PT.json` (neutral) or `theme.json` (themed) |
| R10 | **Rules first** | No code that writes tokens or retires is pushed before the product owner confirms the rules are published (gate after 0.9.1) |

**The standing rules hold:** the Definition of Done in `CONTRIBUTING.md`, CI green before starting the next delivery, and no edits to the release plan or the radar in `ROADMAP.md`.

**Watch out for the deploy.** Every push to `release/0.9` goes live on Pages, so each delivery must leave the app working for the family.

```text
        && resource.data.source == 'adhoc'
        && resource.data.createdBy == resource.data.profileId));
```

### B4. `DataStore` (delivery 0.9.2)

```ts
export interface CompleteTaskInput {
  answer: Answer | null;
  talkFlag: boolean;
  /** Computed by the caller with `tokensFor(task.level, ruleset)`; whole number 1..LIMITS.tokensPerLevelMax, else invalid-argument. */
  tokens: number;
}

// TaskStore
/** One batch: the task moves to done with `tokens`, and its profile gets `increment(tokens)` and `tokensFrom: taskId`. No reward. */
completeTask(worldId, taskId, input: CompleteTaskInput): Write;
/** `canRetire` first (else permission-denied, before any write); then status 'retired', retiredAt now, retiredBy the active profile. */
retireTask(worldId: WorldId, taskId: TaskId): Write;

// New sub-interface: tokens
export interface TokenStore {
  /** The profile's balance (0 when the profile has none yet). The interface calls it only for the active profile (SPEC.md §2). */
  observeBalance(worldId: WorldId, profileId: ProfileId, onValue: Observer<number>, onError?: ObserverError): Unsubscribe;
  /**
   * One batch, for the active profile:
   * - the profile gets increment(-price) and tokensFor;
   * - rewards/{id} is created with the tier, the price, the weekKey of now, and openedAt now;
   * - collectibles/{id} is created with the slot (pending: no nickname, reserveAt null).
   * The id is random and returned at once. The caller passes `priceOf(tier, ruleset)` and a slot drawn with
   * `drawSlot(catalogue, tier, randomInt)`. Before any write: invalid-argument if the price is out of range, or
   * if the balance in the local cache is below it. The server refuses a double spend (`settled` rejects with permission-denied).
   */
  buyReward(worldId: WorldId, input: { tier: Tier; price: number; slot: Slot }): Write<{ rewardId: RewardId }>;
}

// WorldStore: setTierOdds is removed (0.9.5); add
/** Admin only. `tokenRulesProblem` first (invalid-argument). Writes only `ruleset.tokensPerLevel` and `ruleset.tokenPrices`. */
setTokenRules(worldId, rules: Pick<Ruleset, 'tokensPerLevel' | 'tokenPrices'>): Write;
/** Admin only. `isPartySize` first. Nobody is removed from any party. */
setPartySize(worldId, size: number): Write;
```

**Firestore adapter:**

- Use `increment` from `firebase/firestore` with `batch.update(profileDoc, { tokens: increment(n), tokensFrom: taskId })`. Never use `set` on the profile.
- Write rulesets with dotted paths (`'ruleset.tokenPrices'`), as `setShowcaseSize` does.
- `observeBalance` uses `onSnapshot(profileDoc)` and returns `data.tokens ?? 0`.

**Memory adapter.** It must behave like the rules, including offline:

- **Server-side increments.** Add an op `{ collection: 'profiles', id, increment: { tokens: n } }` to `backend.ts`, applied to the committed value at commit time.
  - A balance can be kept in a `balances` map on `WorldState`; how it is stored is the adapter's choice.
  - The batch `check` refuses a result below 0, or a spend by anyone but the owner.
- **Offline.** Add `setOnline(online: boolean)` to the memory store, for tests only:
  - while offline, its view is the committed state at the moment it went offline, plus its own pending batches;
  - its batches are held, and they are committed in order when it comes back online.

**Contract tests** (`src/data/datastore.contract.ts`, both adapters):

- completing earns `tokensFor(level)`: the balance goes 0 → 2 for a `mid` task;
- buying a reward:
  - takes its price from the balance;
  - creates a pending collectible of the chosen tier with the same id;
  - the reward is already opened, and is not in `observeUnopenedRewards`;
- an unaffordable purchase is `invalid-argument`, and nothing changes;
- **the exit criterion** (brief §9):
  - two devices of one profile, both offline, both with a balance of 25, both buy for 25;
  - when they come back online, exactly one purchase stands and the other `settled` rejects with `permission-denied`;
  - both observe a balance of 0 and exactly one new collectible;
- two devices offline, each completing a different task, end with the sum of both;
- retiring:
  - an admin retires a child's task;
  - a child retires their own ad hoc task;
  - a child cannot retire an adult's task or a recurring one;
  - a retired task leaves `observeOpenTasks`;
- `setTokenRules` refuses prices that do not increase; `setPartySize` refuses 0 and 11.

**Emulator test** (`src/data/firestore/firestore.emulator.test.ts`): the same two-offline-devices case on real Firestore, with two app instances signed in on the same profile and `disableNetwork` / `enableNetwork`. CI runs it.
