# Release 0.6 — Rewards: delivery plan

**Start only if the children's pilot passed and the product owner closed 0.5** ([0.5.md](0.5.md)). If 0.5 failed, this release is not built. Work on `release/0.6`, created from `main`.

Read first:

- `CLAUDE.md`;
- `SPEC.md` §4 (`ruleset`, `rewards`, `collectibles`), §5 (rules), §6 ("Completing", "Opening rewards", "Party and reserve") and §8 (themes);
- `docs/architecture.md` §2, §4 (randomness) and §5;
- ADR 0006 (a theme is a skin).

The Firestore rules for rewards and collectibles already exist and are tested (0.1.1). **Do not change `firebase/firestore.rules`.** If a delivery seems to need a rules change, stop and ask the tech lead. Do not edit the release plan or the radar in `ROADMAP.md`.

The Definition of Done in `CONTRIBUTING.md` applies to each delivery (one patch each). Check the CI result, including the emulator tests, before starting the next delivery.

**Delivery mapping.** `ROADMAP.md` lists two deliveries: 0.6.1 (generation and `vault`) and 0.6.2 (opening, `party` and reserve). This plan splits the second into 0.6.2 (opening) and 0.6.3 (party and reserve), so each patch stays testable. The scope does not change.

**Release exit criteria** (`ROADMAP.md`):

- the draw simulation is within its margin (0.6.1);
- opening the same reward on two devices yields a single collectible (0.6.2: contract test, plus a check on real phones);
- a real family Sunday goes by without touching the code.

**Not retroactive.** Tasks completed before 0.6 produce no reward. Rewards start with the first completion after the deploy.

## Decisions for the product owner

**Needed before 0.6.1 starts:**

1. **`tierOdds` for the `low` and `high` levels** (`SPEC.md` §13). The current guess:

   | Level | `low` | `mid` | `high` |
   | --- | --- | --- | --- |
   | `low` | 80 | 17 | 3 |
   | `high` | 45 | 35 | 20 |

2. **How an existing world gets those values.** A world stores its `ruleset` when it is created, so the family's world keeps the defaults it was created with; changing `DEFAULT_RULESET` in code does not reach it. **[proposal]** Add a small admin section, "reward odds", in management. It edits only `tierOdds`, three integers per level that must sum to 100, which the rules already allow. This is a small addition of scope, and it also lets the odds be tuned after a few Sundays. Without it, the only way is a new world.
3. **Is the tier visible before opening?** **[proposal]** Yes. An unopened reward shows the theme's art for its tier, which adds anticipation. The alternative is that every unopened reward looks the same.

**Needed as soon as possible, ideally before the 0.4 pilot:**

4. **The pirate theme package.** `src/themes/pirates/` is empty, and a world's theme is fixed when the world is created (`SPEC.md` §1). If the family's real world is created with the minimal theme, it can never become a pirate world. **[proposal]** Before the pilots, add the pirate theme as data only, which is not an engine feature:
   - names with gender, tiers, character lines and install name, all written by the product owner;
   - a catalogue of at least 3 slots per tier;
   - emoji placeholder art and icons.

   Then create the family's real world with it. The final art arrives in 0.7 by replacing files, with no data migration (ADR 0006). The pirate theme then joins `scripts/validated-themes.json`, as `ROADMAP.md` plans for 0.6.

`ruleset.guarantee` stays `null` (off).

## [x] 0.6.1 — Draw, reward on completion, and the `vault`

### Domain: `src/core/draw.ts`

```ts
/** Extension point for `ruleset.guarantee` (SPEC.md §4). Today it returns ruleset.tierOdds[level]. */
export function tierOddsFor(level: TaskLevel, ruleset: Ruleset): TierOdds;   // throws if ruleset.guarantee !== null: not implemented

/** r = randomInt(100); r < low → 'low'; r < low + mid → 'mid'; otherwise 'high'. */
export function drawTier(odds: TierOdds, randomInt: RandomInt): Tier;        // throws RangeError unless integers summing to 100

/** Uniform among the catalogue slots of that tier (SPEC.md §6). */
export function drawSlot(slots: readonly { slot: Slot; tier: Tier }[], tier: Tier, randomInt: RandomInt): Slot; // throws if the tier has no slot
```

**Acceptance (`src/core/draw.test.ts`):**

1. **Exact mapping,** with a scripted `randomInt` and the odds 80/17/3:

   | `r` | Tier |
   | --- | --- |
   | 0 | `low` |
   | 79 | `low` |
   | 80 | `mid` |
   | 96 | `mid` |
   | 97 | `high` |
   | 99 | `high` |

2. **Invalid odds.** Odds summing to 99 or 101, and a non-integer value, both throw.
3. **`drawSlot`:**
   - it returns only slots of the requested tier;
   - with 3 slots and a scripted `randomInt` returning 0, 1, 2, it returns each slot once;
   - a tier with no slot throws.
4. **Simulation (exit criterion; `SPEC.md` §11).** For each level of `DEFAULT_RULESET`, run 10,000 draws with the real `crypto.getRandomValues` (through `createRandomInt`).
   - **Test:** a chi-square test against the odds, with 2 degrees of freedom, must give a value **below 13.82** (significance 0.001; the margin is fixed in the test, as `SPEC.md` asks).
   - **Why chi-square:** a fixed ± margin would be either too loose for the 3% tier or flaky for the 65% one.
   - **Flakiness:** the chance of a false failure is about 0.3% per run, across the three levels.
5. **`tierOddsFor`:** it returns the ruleset's row, and it throws when `guarantee` is not null.

### Theme: art per reward tier

A new capability for every theme (ADR 0006, rule 4):

- add the required block `"rewardArt": { "low": art, "mid": art, "high": art }` to `schemas/theme.schema.json`;
- give it emoji art in every existing theme (for example 📦, 🎁, 💎);
- `validate-theme` checks it.

### Screens

- **`checkin`.** When a task is completed:
  - draw the tier with `crypto` (`docs/architecture.md` §4);
  - after the character's congratulation, show one line from `src/i18n/pt-PT.json` saying a reward went to the vault, using `{@reward.a}` and `{@vault.the}`, never hard-coded nouns. Still at most 2 taps (`SPEC.md` §2).
- **`vault`.** The map place becomes active. It lists the active profile's unopened rewards only, each with the theme's `rewardArt` for its tier (if decision 3 is yes), grouped by week. No counts are shown to anyone else, and nothing is compared (`SPEC.md` §2). Opening comes in 0.6.2; until then the list is read-only.
- **Reward odds** in management, if decision 2 is yes. Validate with the same rule as `drawTier` before writing.

### Screen

In the `vault`:

- a reward that `canOpen` has an "open" button;
- a reward of the current week before the opening day shows a calm, neutral line from the locale file (for example, it opens on Sunday). It never scolds;
- opening plays a short neutral reveal animation (CSS, the same for every theme), then shows the collectible with its catalogue art, its name and the theme's tier name;
- each person opens only their own rewards.

```ts
export type CollectibleState = 'party' | 'pending' | 'reserve';   // SPEC.md §6 table
export function collectibleState(c: Collectible, partyIds: readonly TaskId[]): CollectibleState;

/** Pending collectibles whose dateKey(now) >= addDays(dateKey(obtainedAt), ruleset.pendingDays). */
export function pendingToReserve(collectibles: readonly Collectible[], partyIds: readonly TaskId[], now: Millis, ruleset: Ruleset): TaskId[];

export interface PartyChange {
  partyIds: TaskId[];      // the new party, in order
  toReserve: TaskId[];     // reserveAt := now
  fromReserve: TaskId[];   // reserveAt := null (they join the party)
}
export type PartyProblem = 'too-many' | 'duplicate' | 'not-owned' | 'inconsistent';
/** Checks a change before it is written: party size, ownership, and toReserve/fromReserve consistent with partyIds. */
export function checkPartyChange(profile: Profile, owned: readonly Collectible[], change: PartyChange, partySize: number): PartyProblem | null;
```

### Contract (tech lead)

```ts
export interface CollectibleStore {
  /** The profile's collectibles, newest first. Owner or admin. */
  observeCollectibles(worldId: WorldId, profileId: ProfileId, onValue: Observer<Collectible[]>, onError?: ObserverError): Unsubscribe;
```

### Screens

The full `home` place (avatar, editing the party at any time, naming collectibles) belongs to 0.7. In 0.6.3:

- **After a reveal:**
  - if the party is not full, two choices: "join the party" or "later" (it stays pending);
  - if the party is full, show the party and ask who leaves (that one goes to the reserve), or "later".

  All text comes from the locale file, with `{@party.the}` and similar placeholders.
- **"Recent" section in the `vault`:** it lists the pending collectibles, with the same choices.
- **Automatic move:** when the app opens and when the `vault` opens, `pendingToReserve` runs for the active profile. Any result is written with `arrangeParty` (same `partyIds`, `toReserve`), silently.
- **Nothing is ever deleted.** No screen offers to delete or release a collectible.

### Acceptance

| Case | Expected |
| --- | --- |
| Add to a party with room | `partyIds` grows; the collectible stays with `reserveAt: null` |
| Add to a full party, choosing who leaves | That one gets `reserveAt` = now; the new one is in `partyIds`; still at most `partySize` |
| A sixth collectible without anyone leaving | `invalid-argument`, before any write |
| A collectible from the reserve back into the party | `reserveAt: null` and in `partyIds` |
| Another profile arranges the party | `permission-denied` |
| UI (memory adapter, injected clock) | A collectible left pending moves to the reserve on the first app open of the next day, and not before |
