# Proposed release 0.8 — Usability: analysis and delivery plan

**Status: approved by the product owner (2026-10-21).** Release order:

1. **0.8 — Usability:** this plan.
2. **0.9 — Rewards that last:** reward pieces, and retiring tasks (part C; both need a rules change).
3. **"Avatar and hardening":** later, still to be planned.

`SPEC.md` was updated with the decisions on 2026-10-21. Start on `release/0.8`, created from `main`.

The analysis comes from the product owner's notes (2026-10-21) and from a review of the code at `v0.7` (`src/ui/`).

---

## A. What is wrong today (findings)

| # | Finding | Where | Effect |
| --- | --- | --- | --- |
| A1 | **Two ways to create a task.** One-shot tasks come from the `board`, one person at a time. Recurring ones come from management, with a multi-person choice where "nobody ticked" means "everyone" | `newTask.ts`, `taskDefs.ts` | Adults must know which door to use, and cannot give a one-shot task to several children at once |
| A2 | **The board alert ignores most cases.** It lights up only for a big task planned for today or tomorrow. Once the planned day passes, the alert disappears although the task is still open. A new task (for example, one an adult just gave a child) lights nothing | `core/alerts.ts`, `map.ts` | The parrot is silent exactly when it should speak |
| A3 | **Two different task lists.** The `board` (title, plan) and the `checkin` (action button first, question inside the card) look and order differently | `board.ts`, `checkin.ts` | The same task looks like two things |
| A4 | **The question is not asked by the character.** It is printed on the task card. The character only reacts to "no" | `checkin.ts` | The `checkin` character, the reason the place exists, is a bystander |
| A5 | **The reserve is reachable only through the `showcase`.** *Correction:* this is the decided design (`SPEC.md` §6, 2026-10-20), not a bug. The product owner confirmed it on 2026-10-21 and changed the limit to the **10** newest: a collectible beyond them "leaves for another island", out of reach but never deleted | `showcase.ts`, `ruleset` | Needs `showcaseSize` 10 and the words that go with it (0.8.5) |
| A6 | **Moving to the reserve is worded as "send to the showcase"** (`home.toReserve`). Two roles are merged in the words but not in the data | `pt-PT.json` | Confusing words for the reserve and the tavern |
| A7 | **The name of a collectible is a separate "change the name" button,** not a label on the creature | `party.ts` (`createRenamer`) | Naming feels like a form, not a game |
| A8 | **Adults cannot see the children's tasks.** `SPEC.md` §7.8 promises "view tasks per profile", but management has no such view | `manage.ts` | No way to check what was done, or to find a task created by mistake |
| A9 | **A task created by mistake can never go away.** The rules allow no delete, no reopen and no cancel. With multi-person creation (A1), one slip creates several stuck tasks | `firestore.rules` | Permanent clutter; erodes trust in the board |
| A10 | **"Done" is irreversible and instant.** A child's mis-tap completes a task forever (done never reopens) | `checkin.ts` | Wrong data; a reward for nothing |
| A11 | **The collection runs out fast** (part C). One reward per task, and 4 collectibles per tier in the pirate catalogue: a child with 3 tasks a day meets every low and mid collectible in about 2 weeks, and then mostly duplicates | `catalog.json`, `SPEC.md` §6 | The game loses its pull |
| A12 | **Small inconsistencies:** "Voltar" at the bottom of every screen (far away on long screens); "Semana 43" in the `vault`, a number children do not know; rewards open one by one; several primary-looking buttons per card | many | Friction |

## B. Deliveries (all interface and domain; no Firestore rules change)

Each delivery is one patch. The Definition of Done in `CONTRIBUTING.md` applies to each, and the developer checks CI before starting the next. The standing rules hold: no change to `firebase/firestore.rules`, and no edit to the release plan or radar in `ROADMAP.md`. Everything stays theme-neutral (ADR 0006), and every text comes from the locale files.

### 0.8.1 — One way to create a task (A1)

**Status: done (0.8.1).**

**One form, `src/ui/screens/taskForm.ts`,** opened from:

- the `board` ("Nova tarefa"), for everyone;
- management ("Nova tarefa" in the recurring list), for adults;
- editing a recurring definition (the same form in edit mode).

| Field | Adult | Child |
| --- | --- | --- |
| **What** (title) | yes | yes (the only field) |
| **For whom** | Chips with each non-archived profile's symbol and name, multi-select, plus an **"Everyone"** chip. There is no default, so at least one choice is required | Always themselves (not shown) |
| **Repeats** | Segmented: **once** · every day · every week · every month. Default: once | Not shown (always once) |
| **Difficulty** | Segmented: low · mid · high. Default: mid | Not shown (mid) |
| **Question** | Collapsed: "+ add a question" | Not shown |
| **Big task (can be planned)** | Shown only when it repeats | Not shown |

**On save:**

| Repeats | What is written |
| --- | --- |
| **once** | One `createAdhocTask` per chosen profile. "Everyone" means every non-archived profile at this moment |
| **every day / week / month** | One `createTaskDef`, with `assignedTo` = the chosen profiles. "Everyone" means `assignedTo: []`, which also includes future profiles; the chip shows a hint saying so |

**Other rules:**

- **Edit mode** (a recurring definition) cannot switch to "once", because a definition is not a task. To stop it, deactivate it, as today.
- **Management** keeps only the list of recurring definitions (edit, deactivate) and opens the same form. The separate creation form goes away.
- **Child limit:** unchanged (`adhocPermission`).

**Acceptance:**

- UI tests (memory adapter):
  - once × 2 children creates 2 tasks;
  - once × Everyone creates one per non-archived profile;
  - weekly × 2 children creates 1 definition with those 2;
  - weekly × Everyone creates `assignedTo: []`;
  - a child sees the title only;
  - the edit mode has no "once";
  - saving with nobody chosen is disabled.
- `newTask.ts` and the creation half of `taskDefs.ts` are removed.

### 0.8.2 — One task card, everywhere (A3)

**Status: done (0.8.2).** The action stays first (left), as the product owner asked in 0.7, instead of on the right; `sortForBoard` takes an `isNew` predicate that 0.8.4 fills, instead of `lastSeen`.

**One component, `src/ui/taskCard.ts`,** used by the `board`, the `checkin` and the adults' view (0.8.7). It shows, in this order:

1. the **title**, large;
2. **chips:** "repeats" (a neutral ↻ glyph plus the cadence word) for recurring tasks; the plan ("Tuesday · after dinner"); and a "?" chip when the task has a question;
3. **one action** on the right, with a touch target of at least 48 × 48 px.

**Same order on every screen:**

1. tasks planned for today or with a past planned day;
2. tasks planned for tomorrow;
3. new tasks (0.8.4);
4. the rest, oldest first.

The code is `sortForBoard(tasks, now, tz, lastSeen)` in `src/core/tasks.ts`, with domain tests. There is no "late" label and no red (`SPEC.md` §2 and rule 6).

**Actions per screen:**

| Screen | Card action |
| --- | --- |
| `board` | "Concluir": opens the `checkin` with this task in focus; the big-task plan stays a secondary link |
| `checkin` | "Feito" (0.8.3 for tasks with a question) |
| adults' view | None (read-only) |

**Acceptance:** UI tests with the same tasks render the same order and chips on the `board` and the `checkin`, and domain tests cover `sortForBoard`.

### 0.8.3 — The character asks the question; undo instead of regret (A4, A10)

**Status: done (0.8.3).**

**Asking the question:**

- **A task without a question:** "Feito".
- **A task with a question:** the card shows the **character's small portrait and a speech bubble with the question,** plus "Sim" / "Não" inside the bubble. The character is the one asking, and it still takes 2 taps from the map (the place, then "Sim").
- **"Não":** the main bubble says one of the theme's `doubt` lines, and the task stays open (unchanged behaviour).

**[decision]** The alternative is that "Feito" first makes the main character ask the question, with "Sim" as a third tap. That breaks the decided 2-tap rule. The tech lead recommends the bubble on the card.

**Undo for 4 seconds.** After "Feito" or "Sim":

- the card shows "Desfazer" for 4 seconds, while the character already congratulates;
- the completion (with its reward) is written when the 4 seconds end, or at once if the page is hidden (`visibilitychange` / `pagehide`, so closing the app does not lose it);
- "Desfazer" within the 4 seconds cancels the write, so nothing is ever reopened in the data (`SPEC.md` §6 holds).

**Acceptance:**

- UI tests with an injected clock:
  - the write happens after 4 s;
  - undo before 4 s writes nothing;
  - hiding the page writes at once;
  - two completions in a row both get written.
- Still 2 taps from the map to a completed task.

### 0.8.4 — The `board` alert that makes sense (A2)

**Status: done (0.8.4).** `boardAlert` takes the loaded definitions and `lastSeen`; "new" for ad hoc tasks compares `createdBy` with the task's own profile.

**Alert states,** strongest first. The code is `boardAlert(tasks, defs, now, tz, lastSeen)` in `src/core/alerts.ts`, which replaces `planAlert`:

| State | When | Look (neutral, every theme) |
| --- | --- | --- |
| `due` | An open task is planned for today, **or its planned day has passed** | Strong glow |
| `new` | An open task the profile has not seen yet (below) | Glow plus a small dot; never a number |
| `soon` | An open task is planned for tomorrow | Soft glow |
| none | None of the above | — |

**What counts as "new":** an open task of the active profile with `createdAt > lastSeen`, that is either:

- an ad hoc task created by someone else (`createdBy` ≠ the profile);
- the first task of a recurring definition created after `lastSeen` (`def.createdAt > lastSeen`).

Daily repeats of a known definition are **not** new, otherwise the alert would be on every morning and mean nothing. **[decision]** Confirm this rule.

**What `lastSeen` is:**

- a per-device, per-profile timestamp in `localStorage` (`fq.lastSeen.{worldId}.{profileId}`), set when the `board` or the `checkin` shows the list;
- on the first run (no value), set it to now, so the alert does not flag everything;
- it is a viewer convenience, so it needs no rules or data change. On a new device, the first visit simply sets it.

**On the `board`,** cards that are new carry a "novo" marker, until the profile leaves the `board`.

**Acceptance:**

- domain tests for each state and the priority, including:
  - planned yesterday and still open gives `due`;
  - planned yesterday but done gives nothing;
  - created by myself is not new;
  - a daily repeat is not new;
  - a new definition is new;
  - no `lastSeen` gives nothing new;
- UI test: the glow appears when an adult creates a task for the child, and goes away after the child opens the `board`.

### 0.8.5 — The crew, end to end (A5, A6)

**The flows to keep and test** (`SPEC.md` §6):

- party → reserve: "send to the tavern", one tap, from the `home`;
- reserve → party: only from the `showcase`, for one's own items, with "who leaves?" when the party is full;
- pending → reserve: after `pendingDays`.

**`showcaseSize` 10:**

- `DEFAULT_RULESET.showcaseSize` becomes 10;
- management gains a "places in the tavern" control (`showcaseSize`, an integer from 1 to 30). It writes the world's `ruleset`, which the rules already allow for an admin. This is how the existing world, created with 30, gets 10.

**"Another island":** an own collectible that drops out of the `showcase` is no longer shown anywhere and cannot be brought back. It stays stored. **No screen says** a collectible is about to leave, and no counts are shown (`SPEC.md` §2).

**Words:**

- moves to the reserve say `{@reserve...}`, never `{@showcase...}`;
- in the pirate theme, `roles.reserve` gets the tavern's name, so the children read "the tavern" for both (a data-only change, ADR 0006).

**Acceptance (UI tests, memory adapter, two devices):**

- party → tavern → party, with a full party (who leaves goes to the tavern);
- pending → tavern on the next day;
- with 11 collectibles in the reserve, the oldest is not in the `showcase` and offers no way back, but `observeCollectibles` still returns it (stored, not deleted);
- changing `showcaseSize` in management takes effect on every device;
- every move is one `arrangeParty`.

### 0.8.6 — Names as labels (A7)

**A name tag on the creature.** Every collectible card (`home`, `vault` reveal, `showcase`) shows its name as a **tag attached to the art**:

- the nickname if there is one, with the catalogue name small under it;
- otherwise the catalogue name, with a dashed "dar um nome" (give a name) tag for the owner.

**Editing:**

- tapping the tag edits it in place (owner, or admin in the `showcase`);
- Enter or blur saves, Escape cancels, and `LIMITS.nickname` applies;
- the separate "mudar o nome" button goes away.

**At the reveal** in the `vault`, the tag is offered at once ("dá-lhe um nome"), as the natural moment to name a new creature.

**Acceptance:** UI tests for naming, clearing (back to the catalogue name), too long, admin moderation in the `showcase`, and a child unable to rename someone else's.

### 0.8.7 — The adults' view of the family (A8)

**In management, "tarefas por perfil":**

- pick a profile;
- see its open tasks (task cards, read-only);
- see the tasks done in the last 7 days, as a list with the day, never a count, ranking or total (`SPEC.md` §2).

This uses `observeTasks` (adults may read every profile's tasks under the current rules). It is also where a mistaken task is found (A9, below).

**Acceptance:** UI test with an adult, two children and tasks in both states. A child device never reaches this screen.

### 0.8.8 — One look and feel (A12)

1. **Top bar on every screen:** back on the left, then the title, then at most one action on the right. Remove the "Voltar" buttons at the bottom. The map keeps its own bar.
2. **Buttons:** one primary button per screen or card. Touch targets of at least 48 px. Base text at least 16 px. Contrast AA.
3. **Empty states** always offer the next step. For example, an empty `board` for an adult offers "Nova tarefa".
4. **`vault` weeks:** "Esta semana", "Semana passada", then a date range ("12–18 out."), never an ISO week number. Add "Abrir todos" when two or more can be opened; the reveals then follow one after the other.
5. **Profile picker:** each profile with its symbol and its `homeVariants` art.
6. **Motion:** respect `prefers-reduced-motion`, so transitions become instant.
7. **Words:** a pass over `pt-PT.json`:
   - one voice: short, positive, never scolding;
   - the same verb for the same act everywhere (Concluir / Feito, Abrir, Enviar, Trazer de volta);
   - themed nouns only through placeholders.

**Acceptance:**

- a screenshot review by the product owner on a phone (all screens);
- UI tests for the relative week labels and "open all";
- `lint:theme-leak` and `validate-theme` pass.

## C. Release 0.9 — Rewards that last (approved scope; planned separately)

`SPEC.md` §6 now specifies both items: **"Retiring a task"** and **"Reward pieces"**. The tech lead will write `docs/plans/0.9.md` before 0.8 closes. Both need a rules change, an ADR, rules tests and a rules deploy by the product owner. In short:

- **Retiring a task:** a "⋯ → retire" action on the task card in the `checkin` (and in the adults' view). It changes `open → retired`: no reward, hidden, never deleted. An adult can retire any open task; a child only their own self-created ad hoc tasks (decided).
- **Reward pieces:**
  - 1 piece per task, 2 for a high task; 4 pieces make a reward;
  - its tier is drawn at opening, from the majority difficulty;
  - nothing expires;
  - the pirate catalogue grows to at least 8 per tier.
