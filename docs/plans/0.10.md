# Release 0.10 — Settings and configuration: delivery plan

**Status:** all deliveries 0.10.1 to 0.10.7 are done in code and documentation (release candidate, 2026-10-24). What is left is the product owner's checks on a phone, listed under 0.10.7 and in the results of 0.10.6. Approved by the product owner (2026-10-24), with every proposal in part D. Work on `release/0.10`.

**Sources:**

- product brief: [0.10-product-brief.md](0.10-product-brief.md), decided 2026-10-24;
- [ADR 0012](../adr/0012-version-check.md): the version and the update.

`SPEC.md` describes the target state, marked "from 0.10". When the plan and `SPEC.md` disagree, ask.

**No Firestore rules change in this release.** The rules already let an admin change a profile's `displayName` and the world's `ruleset` (`firebase/firestore.rules`, the profile and world update rules). So renaming and `pendingDays` need no deploy by the product owner. If a delivery seems to need a rules change, stop and ask.

## A. The rules every delivery keeps

| # | Rule | How 0.10 keeps it |
| --- | --- | --- |
| R1 | **A theme is a skin** (ADR 0006) | The menu, the settings, "Como jogar" and "Como instalar" are neutral screens. Their text is in `pt-PT.json`, with theme terms through `{@…}`. The only theme change is data: the pirate `install.name` and icons. No code looks at the theme id |
| R2 | **Text in locale files** | Every new string goes in `pt-PT.json`. "Como jogar" fills its numbers from the world's `ruleset` through message parameters, never by building sentences in TypeScript |
| R3 | **No counts about people** | "Como jogar" and the menu show no person's count, balance or result. The numbers shown are rules (tokens per level, prices, sizes) |
| R4 | **Admin from the active profile** (ADR 0003) | The "Definições" section and the three settings screens show only to an adult active profile. A settings route opened by a child goes to the map (`replace`), as `manage` does today |
| R5 | **No friction** | The map bar keeps only the greeting and ⚙. Every former management section is 2 taps from the map. Completing a task is untouched |
| R6 | **Local-first** | The menu, "Como jogar" and the settings work offline. The version check fails silently offline (ADR 0012) |
| R7 | **Each push goes live** | Every delivery leaves the app complete for the family. A screen is never left half moved |

The Definition of Done in `CONTRIBUTING.md` applies to every delivery. CI must be green before the next one starts. The release plan and the radar in `ROADMAP.md` are not to be edited.

### B2. The menu (`src/ui/menu.ts`)

```ts
/** The settings menu (brief §1): the panel behind ⚙ on the map. */
export function createMenu(ctx: AppContext, worldId: WorldId): { button: HTMLElement; dispose: Dispose };
```

- **The button:** ⚙ is a `button`, 48 px, with `aria-label` from `menu.open` ("Menu"). In the map bar it replaces "Trocar de perfil", "Gerir" and "Instalar".
- **The panel:** a `<dialog>` opened with `showModal()`. That gives focus handling and Escape for free.
  - It closes with ✕ (`menu.close`), with a tap on the backdrop (`event.target === dialog`), and with the system back gesture (below).
  - It is a panel from the top right, as wide as the screen on a phone, with the safe-area padding. Reduced motion means no animation.
- **Items, in this order** (each item is one full-width row, 48 px):

  | Item | Key | Who | Goes to |
  | --- | --- | --- | --- |
  | Como jogar | `menu.howTo` | everyone | `howTo` |
  | Como instalar | `menu.install` | everyone | `install` |
  | heading "Definições" | `menu.settings` | admin | — |
  | Pessoas | `menu.people` | admin | `people` |
  | Tarefas | `menu.tasks` | admin | `tasks` |
  | Regras do jogo | `menu.rules` | admin | `rules` |
  | Trocar de perfil | `map.switch` | everyone, always last | `profiles` |
  | footer: `menu.version` ("Versão {version} · {date}") and, when newer, "Atualizar" (`menu.update`) | | everyone | ADR 0012 |

  Who counts as admin comes from `observeSelf`, so the list changes while open if the profile changes.
- **The back gesture.** `Navigation` gains one method:

  ```ts
  /** Adds a history entry for an overlay on the current screen. `onBack` runs when the person goes back.
   *  The returned function closes it from the app and removes the entry, without calling `onBack`. */
  pushOverlay(onBack: () => void): () => void;
  ```

  - **In the browser,** it calls `history.pushState({ overlay: true }, '', location.hash)` and listens to `popstate`. The hash does not change, so `hashchange` never fires and the map is not drawn again. Closing from the app (✕, the backdrop) calls `history.back()` once, with the listener already removed.
  - **Tapping an item** closes the panel without going back, and then calls `ctx.go(route, { replace: true })`. That replaces the overlay entry, so back from that screen returns to the map in one step.
  - **`memoryNavigation`** implements it with a stack and a test-only `back()`.
- **Tests (memory adapter):**
  - a child's menu has Como jogar, Como instalar and Trocar de perfil, in that order, and no Definições;
  - an adult's menu has all items, in the order of the table, with Trocar de perfil last;
  - ✕, the backdrop and `back()` each close it and leave the map;
  - an item opens its screen, and one `back()` from there returns to the map;
  - the map bar holds only the greeting and ⚙.

### B3. Settings screens

- **One screen per job.** Each is a `WorldScreen` with the usual `screenBar` (back to `map`), and is admin only (R4).
- **Built from today's sections.** They reuse the sections that exist today in `src/ui/screens/`. `manage.ts` is removed once all three exist (0.10.2).

### 0.10.12 — The invite per child (added by the product owner, 2026-10-24)

The design is in [ADR 0015](../adr/0015-join-link-with-a-child-profile.md), and the product behaviour in brief §2.4. There is no Firestore rules change. The release candidate (0.10.7) is checked again after this delivery.

**Routes** (`src/ui/routes.ts`):

- **The route:** `join` gains `profileId: ProfileId | null`.
- **`parseHash`:**
  - reads `#/join/<worldId>/<themeId>/<profileId>`;
  - ignores any part after the fourth;
  - takes a profile part that is not letters and digits as `null`.
- **`hashFor` and `joinLink(baseUrl, worldId, themeId, profileId = null)`:**
  - write the profile part only when there is a theme part;
  - `joinLink` with a profile and no theme is a programming error and throws.
- **`parseJoinInput`:**
  - returns `{ worldId, themeId, profileId }`;
  - accepts the four-part link, and parts after it, which are ignored;
  - a bare code or a three-part link gives `profileId: null`, exactly as today.

**Store:** `worlds.getProfile(worldId, profileId)` (ADR 0015 §4), in both adapters, with contract tests:

- it returns the profile, archived ones included;
- `null` for an unknown id;
- `permission-denied` for a device that is not a member.

**Joining** (`src/ui/joining.ts`): `joinAndChoose` (ADR 0015 §3–§4), with unit tests. It is used:

- by `renderJoin(route)`, which takes the route instead of only the world id:
  - it passes `route.profileId` with `childOnly: true`;
  - it goes to `map` or `profiles` (`replace`), as the function says;
  - the paste form keeps the profile: `go()` passes the parsed `profileId`;
  - **on iPhone in Safari**, the "Copiar" button copies `joinLink(baseUrl, worldId, themeId, profileId)`, with the profile;
- by `adoptCarry` (`src/ui/app.ts`), with `childOnly: false`, so ADR 0014 keeps its behaviour, through the same code.

`resumeSession` is unchanged. A start at a join link to the world the device is already in goes to the map, or to the picker when there is no profile. In that last case, the profile part of the link applies:

- the route is passed to `joinAndChoose`, which skips the join because the device is already a member;
- if the profile qualifies, the device chooses it and goes to the map.

**Pessoas** (`src/ui/screens/people.ts`, `src/ui/invite.ts`):

- `createInvite(ctx, worldId, profile?: Profile)`:
  - without a profile, it is the general invite, unchanged;
  - with a child profile, it shows:
    - `people.childInviteExplain` ("Este link abre a app já no perfil de {name}. Serve só para entrar pela primeira vez.");
    - the QR code of the child's link and the copy button;
    - **not** the bare code, which would lose the profile.
- **Each non-archived child row** gets "Convidar" (`people.childInvite`), which opens that child's invite in place.
  - Adult rows and archived rows have none.
  - The name appears on the adult's screen only, never in the link.
- **The general "Convidar"** in the bar stays as it is.

**Acceptance (UI tests, memory adapter, several devices):**

- **A new device with a child's link:**
  - lands on the map on that child's profile, with no picker;
  - the same through the paste form, and through a start with the link as the address (an iPhone app added from the link).
- **The general link:** the picker, as today.
- **A device already in the world with a profile:** opening a sibling's link keeps its own profile and goes to the map.
- **A member with no profile yet:** the child's link chooses the child.
- **Fallbacks:** an archived profile, an unknown id, an adult's id, and a malformed part each give the picker, with no error message.
- **iPhone in Safari:** the join screen still asks to install first, and "Copiar" copies the link with the profile.
- **The carry of ADR 0014:**
  - its tests still pass;
  - it still takes an adult profile, because it is the same device's own profile.
- **Pessoas:**
  - "Convidar" is on child rows only;
  - the child's QR encodes the four-part link;
  - the general invite is unchanged.

**On the phones** (with the 0.10.6 check, by the product owner or the developer):

- **Android:** open a child's link on a phone with no app. Install, start, and land on the child.
- **iPhone:**
  1. open a child's link in Safari;
  2. install;
  3. start the app (or tap "Colar" with the copied link);
  4. land on the child.
