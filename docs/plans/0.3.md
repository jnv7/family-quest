## [x] 0.3.1 — Task definitions: data access and management screen

**Contract (tech lead).** Add to `src/data/DataStore.ts`, then to both adapters and the contract suite:

```ts
export interface TaskDefInput {
  title: string;
  cadence: Cadence;
  level: TaskLevel;
  /** Empty means every non-archived profile. */
  assignedTo: ProfileId[];
  question: string | null;
  big: boolean;
}

export interface TaskDefStore {
  /** Every definition, active and inactive, ordered by title. */
  observeTaskDefs(worldId: WorldId, onValue: Observer<TaskDef[]>, onError?: ObserverError): Unsubscribe;
  /** Admin only. Created active. */
  createTaskDef(worldId: WorldId, input: TaskDefInput): Write<{ defId: TaskDefId }>;
  /** Admin only. Definitions are never deleted: deactivate them with `active: false`. */
  updateTaskDef(worldId: WorldId, defId: TaskDefId, patch: Partial<TaskDefInput & { active: boolean }>): Write;
}

export interface DataStore {
  // ...existing members
  readonly taskDefs: TaskDefStore;
}
```

**Screen.** A "recurring tasks" section in management (admin only):

- a list of definitions, inactive ones dimmed;
- create and edit, with title, cadence, level, for whom (everyone, or chosen profiles), optional question, and "big";
- activate and deactivate. There is no delete.

All text comes from `src/i18n/pt-PT.json`.

**Acceptance (contract suite, both adapters):**

| Case | Expected |
| --- | --- |
| An admin creates a definition | `observeTaskDefs` emits it with `active: true`, on every device |
| A device on a child profile creates or updates one | `permission-denied` |
| An admin deactivates and reactivates one | Both changes are emitted |
| A title over `LIMITS.title`, or a question over `LIMITS.question` | `invalid-argument`, before any write |
| Editing a definition | Existing tasks keep their old title, level and question; only new tasks copy the new values |

## [x] 0.3.2 — Generation rule (pure domain)

Create `src/core/generation.ts`:

```ts
export interface NewRecurringTask {
  id: TaskId;            // recurringTaskId(defId, periodKey, profileId)
  defId: TaskDefId;
  periodKey: PeriodKey;
  profileId: ProfileId;
  title: string;         // copied from the definition
  level: TaskLevel;      // copied
  question: string | null; // copied
}

export interface GenerationInput {
  profile: Profile;                 // the active profile
  defs: readonly TaskDef[];         // every definition of the world
  tasks: readonly Task[];           // every task of this profile known to the device (open and done)
  now: Millis;
  timeZone: string;                 // ruleset.timezone
}

/** The tasks to create now, sorted by `defId`. Pure and idempotent. */
export function recurringTasksToCreate(input: GenerationInput): NewRecurringTask[];
```

A definition yields a task for the current period only if all of these hold (`SPEC.md` §6):

1. the definition is `active`;
2. the profile is not archived;
3. `assignedTo` is empty or contains the profile;
4. no task from this definition for this profile is `open`, from any period;
5. no task from this definition for this profile was completed in the current period, meaning `periodKey(cadence, doneAt) === periodKey(cadence, now)`;
6. no task with the same id exists already.

Acceptance: `src/core/generation.test.ts` covers every row below. The setup for every row:

- `now` = `2026-10-19T09:00:00Z`, which is Monday 10:00 in Lisbon (`dateKey` `2026-10-19`, `weekKey` `2026-W43`, `monthKey` `2026-10`);
- profile `p1` (child, not archived);
- `daily` = an active daily definition with `assignedTo: []`, unless the row says otherwise.

| # | Definitions | Existing tasks of `p1` | Expected ids |
| --- | --- | --- | --- |
| 1 | `daily` | none | `daily_2026-10-19_p1` |
| 2 | `daily` | `daily_2026-10-17_p1`, open | none (one open task per definition) |
| 3 | `daily` | `daily_2026-10-17_p1`, done at `2026-10-19T08:00:00Z` | none (an overdue task completed today covers today) |
| 4 | `daily` | `daily_2026-10-17_p1`, done at `2026-10-18T20:00:00Z` | `daily_2026-10-19_p1` |
| 5 | `daily` | `daily_2026-10-19_p1`, done today | none (idempotent) |
| 6 | `weekly` | none | `weekly_2026-W43_p1` |
| 7 | `weekly` | `weekly_2026-W42_p1`, done at `2026-10-19T08:00:00Z` | none |
| 8 | `monthly` | none | `monthly_2026-10_p1` |
| 9 | `daily` with `active: false` | none | none |
| 10 | `daily` with `assignedTo: ['p2']` | none | none |
| 11 | `daily` with `assignedTo: ['p1', 'p2']` | none | `daily_2026-10-19_p1` |
| 12 | `daily`, but the profile is archived | none | none |

## [ ] 0.3.3 — Generating on app open and on profile switch

**Contract (tech lead).** Add to `TaskStore`:

```ts
/**
 * Creates each task with its deterministic id, one write per task (not one
 * batch: a rejected task must not block the others). Rejections with
 * `permission-denied` or `already-exists` are expected and silent (SPEC.md §10);
 * `settled` rejects only on any other error.
 */
createRecurringTasks(worldId: WorldId, tasks: readonly NewRecurringTask[]): Write;

/**
 * Resolves once this profile's tasks have been read from the server at least
 * once since the app started. It never resolves while offline.
 * Firestore: onSnapshot with includeMetadataChanges, until metadata.fromCache is false.
 */
whenTasksSynced(worldId: WorldId, profileId: ProfileId): Promise<void>;
```

**When to generate**, in `src/ui/`, for the active profile, after the app opens and after every profile switch:

1. Wait for `whenTasksSynced`, for at most 5 seconds (**[proposal]**). This avoids generating from an empty cache, which is the known edge case in `SPEC.md` §6.
2. Read the definitions and the profile's tasks (the latest observer values), and call `recurringTasksToCreate`.
3. Call `createRecurringTasks` with the result. Never await `settled` before showing the board.

**Board** (`SPEC.md` §7):

- it shows every open task, past periods included;
- it shows at most one open task per definition and profile, the oldest one;
- ad hoc and recurring tasks appear together, oldest first.

**Acceptance:**

- **Contract suite (both adapters):**
  - `createRecurringTasks` with a task that already exists (open or done) leaves it unchanged, and `settled` resolves;
  - two devices on the same profile generating at the same time end with one task;
  - a definition edited after a device cached it: the creation is rejected silently, and the next generation, after sync, creates it with the new values.
- **UI tests (memory adapter):**
  - opening the app creates today's daily task once; opening again creates nothing;
  - switching to another profile generates that profile's tasks;
  - with two open tasks for one definition (the edge case), the board shows only the oldest one.

## [ ] 0.3.4 — Planning big tasks

**Contract (tech lead).** Add to `TaskStore`:

```ts
/** Owner only, on an open task whose definition is `big`. `null` clears the plan. */
setPlan(worldId: WorldId, taskId: TaskId, plan: Plan | null): Write;
```

**Domain** (`src/core/plan.ts`): `validatePlan(task, def, plan, now, timeZone)` returns `'ok' | 'not-big' | 'date-out-of-range' | 'trigger-invalid'`. The rules are:

- the task's definition is `big`;
- `plan.date` is between today and the last day of the task's period, inclusive (**[proposal]**);
- `plan.trigger` is 1 to `LIMITS.trigger` characters of free text (for example, "depois do jantar").

**Screen.** On a big open task, the owner opens a "plan" control from the `board`: pick a day, and write or pick a trigger. Changing or clearing the plan has no penalty and leaves no visible record (`SPEC.md` §6). Two to three trigger suggestions come from `src/i18n/pt-PT.json`.

**Acceptance:**

- domain tests for every `validatePlan` outcome, including the last day of a week (Sunday) and of a month;
- contract suite: an owner sets and clears a plan; another profile setting one gets `permission-denied`; a plan on a task that is not big gets `invalid-argument` before any write.

## [ ] 0.3.5 — Visual alert

**Domain** (`src/core/alerts.ts`): `planAlert(tasks, now, timeZone)` returns `'today' | 'tomorrow' | null`, for the open tasks of the active profile:

- `'today'` if any open task has `plan.date` = today;
- otherwise `'tomorrow'` if any has `plan.date` = tomorrow;
- otherwise `null`.

**Screen:**

- the `board` place on the map lights up when `planAlert` is not null. The alert is a neutral CSS effect, the same for every theme, with two intensities, and it is not themed (ADR 0006);
- on the `board`, the planned tasks for today and tomorrow are highlighted;
- no text scolds, and there are no notifications (`SPEC.md` §2).

**Acceptance:**

- domain tests: today, tomorrow, both (today wins), a done task (ignored), and the day boundary at `2026-10-25T23:00:00Z` versus `2026-10-26T00:00:00Z`;
- UI test: the map place gets the alert state, and loses it once the planned task is completed.
