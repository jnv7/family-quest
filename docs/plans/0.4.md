# Release 0.4 — Adult pilot (7 days): plan

**Start only after the product owner closes 0.3** ([0.3.md](0.3.md)). The developer works on `release/0.4`, created from `main`.

This release builds **no new features** (`ROADMAP.md`). The product owner runs a real week of use with the adults only; the developer only fixes what the pilot breaks.

**Exit criteria** (`ROADMAP.md`):

- the app is opened before dinner on at least 5 of the 7 days;
- no completion is lost.

## Privacy, first

The repository is public (`CLAUDE.md` rule 2):

- **Outside the repository:** the daily log and every raw note (a note on the phone, paper, a private document).
- **In the repository:** only the final, anonymised report (`docs/pilots/0.4.md`, template below). It uses "Adult A", "Adult B", and no names, times of personal routines or task titles that identify the family.

## Roles

| Who | Does |
| --- | --- |
| Product owner | Prepares the pilot, keeps the daily log, decides what is a blocker, writes the report, decides the exit |
| Second adult | Uses the app every day and tells the product owner about friction |
| Developer | Fixes the bugs the product owner reports, as patches `0.4.x`. Builds nothing else |
| Tech lead | Triage: classifies each report as a bug, a change of scope or an idea for the radar. Reviews the fixes and the report |

## [ ] A. Before day 1 (product owner)

1. **Phones.** Both adults have the app installed from the live address (`https://www.jnvasconcelos.com/family-quest/`) and their own adult profile chosen.
2. **Recurring tasks.** Create the adults' recurring tasks for the week in management: at least 3 daily ones, 1 weekly, and 1 big weekly one with a plan, so every part of 0.3 is used. Ad hoc tasks are created as life asks for them.
3. **"Before dinner".** Agree on what it means (for example, before 20:00).
4. **Daily log.** Set it up outside the repository, using the template in section C.
5. **Pick the 7 days.** Avoid a week with travel, and note that a Sunday is included.

## [ ] B. During the 7 days

- **Every day:** each adult uses the app as part of their day. The product owner fills one log row per adult per day, ideally at bedtime.
- **When something breaks or annoys:** write it down at once (what you did, what you expected, what happened, the phone, whether there was a network). Send it to the tech lead the same day.
- **Triage** (tech lead, the same day):

  | Kind | Example | What happens |
  | --- | --- | --- |
  | **Blocker** | A completion lost, cannot complete, the app does not open, a duplicate task | The developer fixes it at once as a patch. The deploy is automatic, and phones take it on their next launch (ADR 0004) |
  | **Bug** | Wrong text, a layout glitch, a slow screen | Fixed during the week if small; otherwise right after |
  | **Change or idea** | "It would be nice if..." | Not built. The tech lead records it for the product owner, who decides whether it goes on the radar |

- **Proof of "no completion lost":** at least twice during the week, complete a task in airplane mode, close the app, and turn the network back on later. Note each one in the log, and check it appears as done on the other adult's phone, in management.

## C. Daily log template (keep it outside the repository)

| Date | Adult | Opened before dinner? | Tasks completed | Of which offline | Anything lost or duplicated? | Friction (more than 2 taps, unclear text, waiting) |
| --- | --- | --- | --- | --- | --- | --- |
| | A | yes / no | | | | |
| | B | yes / no | | | | |

The app does not record when it is opened, and adding that would be a new feature, so "opened before dinner" comes from this log.

## [ ] D. Day 7: check and report (product owner, with the tech lead)

1. **Completions.** In management, for each adult, compare the completed tasks of the week with the log, especially the offline ones. Any completion in the log that is missing in the app means a completion was lost.
2. **Usage.** Open Firebase console → Firestore → Usage for the week. Write down the daily peak of reads and writes: the free limit is 50,000 reads/day.
3. **Report.** Write `docs/pilots/0.4.md`, anonymised:

   ```markdown
   # Pilot 0.4 — adults — report

   - Dates: <week>
   - Participants: Adult A, Adult B

   ## Exit criteria
   | Criterion | Result | Met? |
   | --- | --- | --- |
   | Opened before dinner on ≥5 of 7 days | A: n/7, B: n/7 | yes / no |
   | No completion lost | n offline completions checked, n lost | yes / no |

   ## Usage
   Peak reads/day, peak writes/day.

   ## Friction and bugs
   What happened, and what was fixed (patch numbers).

   ## Ideas raised (not built)
   For the product owner to decide on the radar.
   ```

4. **Decision** (product owner):
   - **if both criteria are met,** close 0.4 (`GOVERNANCE.md` §3), and the children's pilot follows ([0.5.md](0.5.md));
   - **if not,** decide whether to fix and repeat the week, or to change course.

## Outcome (2026-10-20)

The pilot ran and met its exit criteria, according to the product owner. By the product owner's choice, no detailed pilot report is recorded. The release was closed as `v0.4`.
