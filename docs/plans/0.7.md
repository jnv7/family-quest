# Release 0.7 — `home`, `showcase` and art: delivery plan

**Start only after the product owner closes 0.6.** Work on `release/0.7`, created from `main`.

Read first:

- `CLAUDE.md`;
- `SPEC.md` §2 (no comparison), §6 ("Party and reserve", "Showcase"), §7 (screens 5 and 7) and §8 (themes, children's drawings);
- `docs/architecture.md` §6;
- ADR 0004 (offline app shell) and ADR 0006 (a theme is a skin).

The rules are the same as in every release:

- **Firestore rules:** the rules for this release already exist and are tested. **Do not change `firebase/firestore.rules`**; if something seems to need it, stop and ask the tech lead.
- **Roadmap:** do not edit the release plan or the radar in `ROADMAP.md`.
- **One patch per delivery:** the Definition of Done in `CONTRIBUTING.md` applies to each delivery.
- **CI:** check the result, including the emulator tests, before starting the next delivery.

**Not in this release** (it is 0.8): the layered avatar, the PIN, JSON export, and polishing the install experience. The `home` shows an empty, labelled place where the avatar will go.

**Release exit criteria** (`ROADMAP.md`):

- licences are checked, and `CREDITS.md` is complete (0.7.3, 0.7.4);
- the map loads in under 3 seconds on Wi-Fi (0.7.6, measured last, on the final map).

## Decisions (product owner, 2026-10-20)

1. **No children's drawings in this release.** The children choose the art from a short, prepared list of images, which may be emoji. Drawings stay a possibility for later (`SPEC.md` §8), on the radar. Because of this:
   - every image file in the repository is CC0 (Kenney) or made for this repository (MIT);
   - there is no new licence, and there are no consent or drawing-privacy steps.
2. **Kenney packs for the pirate theme** (all CC0, 2D, PNG; `art:prepare` converts them to `webp`). These are the tech lead's recommendation; the product owner and the children pick the actual pieces:

   | Pack | Use in the theme |
   | --- | --- |
   | [Pirate Pack](https://kenney.nl/assets/pirate-pack) (190 files: top-down ships and tiles) | The map background, assembled from sea and island tiles into one image; the `homeVariants` (a large ship for adults, a small boat for children); the places |
   | [Fish Pack](https://kenney.nl/assets/fish-pack) (120 files, underwater) | Sea collectibles |
   | [Animal Pack](https://kenney.nl/assets/animal-pack) (80 files) | Land and island collectibles, so the catalogue is not only fish |
   | Emoji | Whatever the packs lack: the lighthouse, the `checkin` character, the reward art per tier (for example 📦 🎁 💎), and any collectible the children prefer as emoji |

   - **Collectibles:** pick at least 3 per tier (the catalogue has 4 per tier today). Keep the existing slot ids; only the `art` changes.
   - **Emoji:** emoji are drawn by each phone's system font, so they look different on iPhone and Android, and they need no file and no credit. Image files look the same everywhere.
   - **Not used:** "UI Pack - Adventure" (panels and buttons). The interface's look is the engine's, the same for every theme (ADR 0006); themes have no panel art.
3. **All three themes ship** (`minimal`, `minimal-farm`, `pirates`).
4. **Art budgets**, checked by `validate-theme`:

   | Asset | Limit |
   | --- | --- |
   | Map background | 1 file, at most 1080 × 1920, at most 400 KB |
   | Place art, `homeVariants`, character, reward art | at most 512 × 512, at most 80 KB each |
   | Collectible art | at most 512 × 512, at most 60 KB each |
   | All art of one theme | at most 2.5 MB |

   Format: `webp` for raster art, `svg` for vector. `png` only for install icons.
5. **Admin moderation of nicknames.** The `showcase` shows nicknames to everyone, so the admin view gets a "rename" action on any collectible. It is not a delete. The rules already allow it.

## [x] 0.7.1 — The `home`

### Contract (tech lead)

Add to `CollectibleStore`:

```ts
/**
 * Sets or clears a collectible's nickname (SPEC.md §4). The text is trimmed;
 * empty means null; longer than LIMITS.nickname is invalid-argument before
 * any write. Owner, or an admin (moderation).
 */
setNickname(worldId: WorldId, collectibleId: TaskId, nickname: string | null): Write;
```

### Domain: `src/core/collection.ts`

```ts
/** The name to show: the nickname, or else the catalogue slot's name in the active theme. */
export function displayName(c: Collectible, slotName: (slot: Slot) => string): string;

/** The profile's collectibles, split by state (party in partyIds order; pending and reserve newest first). */
export function collectionOf(owned: readonly Collectible[], partyIds: readonly TaskId[]): {
  party: Collectible[]; pending: Collectible[]; reserve: Collectible[];
};
```

**Acceptance (domain tests):**

- `displayName`: with a nickname, it returns the nickname; with null, the slot name.
- **Slot missing from the theme catalogue:** this happens when a collectible comes from a theme that no longer has the slot. Slots are permanent, so this is a bug: `displayName` throws, and the UI test shows that the screen catches it and shows the tier name instead of crashing.
- `collectionOf`:
  - the three states are split as in `SPEC.md` §6;
  - the party follows the order of `partyIds`;
  - a `partyIds` entry the profile does not own is ignored, and reported with `console.error` (explicit failure, not silent).

### Screen: the `home` place

The `home` place on the map becomes active. For the active profile, it shows:

- the theme's `homeVariants` art for the profile's `kind`, with `displayName`;
- the avatar place: empty, labelled from the locale file ("coming soon", without a date);
- **the party,** up to `partySize`. Each member has:
  - its art, name and tier name;
  - "rename", which edits the nickname inline (`LIMITS.nickname`);
  - "to the reserve", one tap with no confirmation, because nothing is lost.
- **pending collectibles,** if any, with the same choices as in the `vault` (0.6.3);
- **the reserve,** newest first. Each item has "to the party". If the party is full, the screen asks who leaves, as in 0.6.3.

Every move uses `collectibles.arrangeParty`, and every name change uses `setNickname`. All text comes from `src/i18n/pt-PT.json`, with themed nouns as placeholders (`{@party.the}`, `{@reserve.the}`, `{@home}`). No counts are shown ("12 in the reserve"), and nothing is compared with anyone (`SPEC.md` §2).

**Acceptance:**

| Case | Expected |
| --- | --- |
| The owner renames, then clears the name | The name shows, then the catalogue name shows again |
| A name of 31 characters, or only spaces | `invalid-argument` before any write; spaces only clear the name |
| An admin renames another profile's collectible | Allowed (moderation) |
| A child renames another profile's collectible | `permission-denied` |
| Party → reserve, then reserve → party with a full party | The leaver goes to the reserve; the party never exceeds `partySize` |
| UI test (memory adapter) | The `home` shows party, pending and reserve correctly after each of the moves above, on two devices |

## [x] 0.7.2 — The `showcase`

### Contract (tech lead)

```ts
export interface ShowcaseItem {
  /** Only what the showcase may show: never profileId (SPEC.md §2, §6). */
  id: TaskId;
  slot: Slot;
  tier: Tier;
  nickname: string | null;
  reserveAt: Millis;
}

/**
 * The world's collectibles with reserveAt set, newest first, at most `limit`
 * (ruleset.showcaseSize). Any member. Firestore: where('reserveAt', '!=', null),
 * orderBy('reserveAt', 'desc'), limit.
 */
observeShowcase(worldId: WorldId, limit: number, onValue: Observer<ShowcaseItem[]>, onError?: ObserverError): Unsubscribe;
```

The adapter maps each document to `ShowcaseItem`, so `profileId` never reaches the UI. Anyone with the data can still read it, by design (`SPEC.md` §5); the interface never shows it.

### Screen: the `showcase` place

The `showcase` place on the map becomes active:

- it shows a grid of up to `showcaseSize` items, each with its art and `displayName`;
- it shows **no owner, no date and no count**;
- tapping an item shows it larger, with its name and tier name, and nothing else;
- an admin also sees "rename" (decision 5).

**Acceptance:**

| Case | Expected |
| --- | --- |
| Three profiles move collectibles to the reserve | The showcase lists them all, newest `reserveAt` first, on every device |
| More than `showcaseSize` in the reserve | Only the newest `showcaseSize`; the others stay stored (nothing is deleted) |
| A collectible goes back to the party | It leaves the showcase |
| A test inspects `ShowcaseItem` objects | No `profileId` field, in both adapters |
| The rendered DOM of the showcase | Contains no profile `displayName` (UI test with known names) |

## [x] 0.7.3 — Art pipeline, budgets and credits

### Script: `npm run art:prepare`

The script `scripts/art-prepare.ts` uses `sharp` as a dev dependency; its prebuilt binaries need no install script.

- It reads source images (the downloaded Kenney PNGs) from a folder **outside the repository**, given as an argument (for example `npm run art:prepare -- ~/family-quest-art/pirates`). The downloaded packs are not committed; only the processed files are.
- It writes `webp` files to `src/themes/{themeId}/assets/`:
  - resized to the budget of each kind (decision 4);
  - with **all metadata stripped** (EXIF, XMP, ICC beyond sRGB).
- Which kind each file is comes from a small mapping file next to the sources (`art.json`: source file → target path → kind). The mapping file stays outside the repository too.

### Credits: `src/themes/{themeId}/credits.json`

Add `schemas/credits.schema.json`. The file lists every image in the theme's `assets/`:

```json
{
  "$schema": "../../../schemas/credits.schema.json",
  "assets": [
    { "file": "assets/map.webp", "author": "Kenney (kenney.nl)", "source": "https://kenney.nl/assets/<pack>", "licence": "CC0-1.0" },
    { "file": "assets/collectibles/c-low-01.webp", "author": "Kenney (kenney.nl)", "source": "https://kenney.nl/assets/fish-pack", "licence": "CC0-1.0" }
  ]
}
```

- **No family names in `author`.**
- **Allowed licences:** `CC0-1.0`, and `MIT` for art made for this repository. Adding any other licence is a decision for the product owner.

### `validate-theme` additions

These run for every shipped theme:

1. **Credits:** every file in `assets/` has exactly one `credits.json` entry, and every entry points to an existing file.
2. **Licences:** every licence is in the allowed list.
3. **Budgets:** each file is within its kind's size and pixel limits, and the theme total is within budget (decision 4).
4. **Metadata:** no `webp` or `png` contains EXIF or XMP chunks (`EXIF`, `XMP ` in webp; `eXIf`, `iTXt` with XMP in png).
5. **Formats:** raster art is `webp`, and `png` is used only under `assets/icons/`.

### `CREDITS.md`

`npm run credits` generates it at the repository root from every `credits.json`, grouped by theme and by author, with the licence texts linked. CI checks that the generated file equals the committed one, so it can never go stale.

**Acceptance:**

- broken fixtures fail each of the 5 checks with a message naming the file (built in a temporary folder by `scripts/theme-assets.test.ts`, so no binary test files are committed);
- a test image with EXIF (a fixture) is stripped by `art:prepare`;
- `CREDITS.md` exists and is up to date in CI.

The existing emoji themes have no image files except their icons, which get `credits.json` entries (`MIT`, made for this repository).

## [x] 0.7.5 — Moorings and profile symbols

Added on 2026-10-20 at the product owner's request (`SPEC.md` §7, "Moorings"; §4, `avatar.symbol`; §8). The developer proposed the moorings, and the tech lead settled the open questions as follows.

### Data (no Firestore rules change)

- **Model.** `Avatar` in `src/core/model.ts` gains `symbol: string | null`, and `DEFAULT_AVATAR.symbol` is `null`. The converters read a profile without `symbol` as `null`; `schemaVersion` stays 1, because the field is additive and optional on read.
- **Rules.** `firestore.rules` only checks `avatar is map`, so no rules change is needed. Prove it with one rules test, an owner writing `avatar.symbol`, which must pass without editing the rules.
- **Contract (tech lead).** Add to `WorldStore`:

  ```ts
  /** Owner or admin. `symbol` must be one of the theme's profileSymbols, or null; otherwise invalid-argument before any write. */
  setProfileSymbol(worldId: WorldId, profileId: ProfileId, symbol: string | null): Write;
  ```

  `CreateProfileInput` gains an optional `symbol`.

### Theme schema

```json
"profileSymbols": ["🐬", "🦀", "🐙", "..."],            // required, at least 12, unique
"map": {
  "background": ...,
  "aspectRatio": ...,
  "moorings": {                                          // optional
    "child": {                                           // optional per kind: "adult", "child"
      "spots": [ { "x": 0, "y": 0, "width": 0, "height": 0 } ],   // percent of the map, like places
      "symbolAt": { "x": 50, "y": 35, "size": 30 }      // percent of a spot (centre and size of the emoji)
    }
  }
}
```

- **Every theme** gets `profileSymbols`:
  - the emoji themes can use neutral emoji (animals, objects);
  - the pirate theme can use themed ones, chosen by the children.
- **The pirate theme** declares `moorings.child` with at least 6 spots along the pier. It declares no `moorings.adult`, so adults keep the large ship as the `home` place art.
- **Pirate map art.** The example boats are removed from the map image, and the moorings replace them. This change touches only `src/themes/pirates/`.

### `validate-theme` additions

1. Every spot lies inside the map (`x + width <= 100`, `y + height <= 100`) and has a positive size.
2. Spots of the same kind do not overlap each other.
3. `symbolAt` lies inside the spot.
4. `profileSymbols` has at least 12 entries, without duplicates, and each entry is a single emoji (one grapheme cluster, checked with `Intl.Segmenter`).

### Changes after the product owner's review (2026-10-20)

These replace the matching lines below and are recorded in `SPEC.md` and `CHANGELOG.md`:

- **Any emoji, not only the theme's.** `setProfileSymbol` and `createProfile` accept any single emoji (`invalid-argument` otherwise), so the adapters no longer need the theme's list. `profileSymbols` stay as suggestions.
- **The `home` is the avatar for now.** Its boat shows the symbol on the sail (new optional `homeSymbolAt` in the theme), a button under it opens a panel with every emoji, and the empty avatar place is removed.
- **The alert** on the map is a speech bubble with dots (SPEC §1).
- **No reserve on the profile.** Sent-away collectibles are only seen in the `showcase` (SPEC §6). The *To the party* choice for the reserve in the `home`, above, is gone; the data keeps the way back.
- **Symbol picker:** the theme's suggestions, then animals and plants only.
- **The adults' symbols** appear on the big ship at the pier, for everyone (new optional `symbolAt` on a place).
- **From the `showcase`,** a person brings their own collectibles back into the party.
- **`checkin` and `board`:** task cards; the completing button comes first; "I did better" is a static line, not a button.

*Open for the tech lead:* `homeSymbolAt` is a new optional field in the theme schema.

### Domain: `src/core/moorings.ts`

```ts
export interface MooredBoat { kind: ProfileKind; spotIndex: number; symbol: string | null; own: boolean; }

/** Non-archived profiles of each kind with moorings, in creation order (createdAt, then id), one per spot; the extras are left out. */
export function mooredBoats(profiles: readonly Profile[], moorings: ThemeMoorings | undefined, activeProfileId: ProfileId | null): MooredBoat[];
```

`MooredBoat` deliberately carries no `profileId` and no name. The map needs only the kind, the spot, the symbol, and whether the boat is the active profile's own (`own`), which makes it tappable.

### Screen

- **Data:** the map observes the world's profiles with `worlds.observeProfiles`. The device's own membership is not enough, because the boats need every profile. The map renders at once from the theme, and the boats appear when the profiles arrive. The map never waits for them, which matters for 0.7.6.
- **Boats:**
  - **The active profile's own boat** is a button that opens the `home`, with the same transition as the `home` place. Its accessible label comes from the locale file.
  - **Every other boat** is decorative, with `aria-hidden="true"` and `pointer-events: none`.
  - No boat covers or blocks a tappable place.
- **Symbol:** the emoji is drawn at `symbolAt`. With no symbol, the sail is plain.
- **Choosing a symbol:**
  - in the `home`, the owner chooses or changes it from a grid of `profileSymbols`;
  - in management, an adult can choose it when creating a profile;
  - all text comes from the locale file.

### Acceptance

| Case | Expected |
| --- | --- |
| 0 children | No boat at the pier; the map is otherwise unchanged |
| 1 child, with a symbol | One boat at the first spot, with that emoji on the sail |
| More children than spots | One boat per spot, in creation order; the extras are not drawn and nothing fails |
| An archived child | Not drawn; the next child moves up a spot |
| Same profiles on two devices | Same spots, same symbols (deterministic order) |
| A theme without `moorings` (`minimal`, `minimal-farm`) | The map's DOM is the same as before this delivery |
| Tapping your own boat | Opens your `home` |
| Tapping another person's boat | Nothing happens; the place underneath (if any) still receives taps |
| Switching profile | The newly active profile's boat becomes the tappable one |
| Rendered DOM of the map | Contains no profile `displayName` |
| `setProfileSymbol` with an emoji outside `profileSymbols` | `invalid-argument` before any write |
| A child sets another profile's symbol | `permission-denied` |
| `validate-theme` fixtures | A spot outside the map, overlapping spots, `symbolAt` outside its spot, and a duplicate symbol each fail, naming the file and path |

## [ ] 0.7.6 — Load time

**Measure** (product owner, with the developer). On a mid-range Android phone over Wi-Fi:

- clear the site data (so there is no service worker cache), then open the app;
- time from the tap to the moment the map is shown and its places respond. Repeat 3 times, and also once from the installed app with its cache.

Use Chrome remote debugging (Performance panel), or a screen recording. Write the numbers in the delivery notes.

**Target:** under 3 seconds on the first, uncached load (exit criterion).

**If the target is missed,** fix it in this order, measuring after each step. **Do not** add dynamic `import()` after start-up (ADR 0004).

1. Shrink art: make the map background smaller, and lower the `webp` quality.
2. Make sure the map does not wait for Firestore: it renders from the theme and the cached membership, and data fills in afterwards.
3. Defer the service worker registration until after the map is shown (it already registers on `load`; check that it is not earlier).
4. Only then talk to the tech lead about splitting the bundle.

**Acceptance:**

- the measured numbers are recorded, and all are under 3 seconds;
- the production bundle size and the precache size are written in the `CHANGELOG.md` entry, so 0.8 can compare.
