# 0001 — Founding decisions

- **Status:** Accepted. Decision 6, "Roles", is superseded by [ADR 0003](0003-admin-rights-from-profile.md).
- **Date:** 2026-10-18
- **Decided by:** product owner

## Context

Family Quest is a task and reward app for one family, used on the phones of adults (iPhone) and children (Android). It must cost nothing to run. It must work offline, and it must stay easy to re-theme. The specification is in `SPEC.md`. This record captures the decisions that the rest of the project builds on.

## Decisions

1. **Hosting and backend.**
   - **Decision:** a static PWA on GitHub Pages, with data in Firebase on the Spark (free) plan, using only Firestore and anonymous Authentication.
   - **Excluded:** Cloud Functions and Cloud Storage, because they require billing.
2. **Public repository.**
   - **Decision:** the repository is public, because GitHub Pages on a free account requires it.
   - **Consequence:** no secret or personal family data may ever enter the repository.
   - **Firebase config:** the `firebaseConfig` is public by design; access control lives entirely in the Firestore rules.
3. **Stack.** TypeScript in strict mode, Vite, no UI framework, Vitest, and the modular Firebase SDK from npm.
4. **Layering.**
   - **Domain:** pure domain logic in `src/core/`, with no Firebase and no DOM.
   - **Data access:** only through an intent-based `DataStore` interface, with a Firestore adapter and an in-memory adapter. The interface and the schema are kept independent of Firestore, so a different database can replace it later.
5. **Local-first without transactions.**
   - **Problem:** Firestore transactions do not run offline.
   - **Decision:** state changes that must work offline use `writeBatch`. Uniqueness comes from deterministic document ids (a task's id is reused for its reward and its collectible) and from "create, never replace" rules.
6. **Identity and access.**
   - **Devices:** each device signs in anonymously. The random world id is the access code, shared as a link or QR code with the code in the URL fragment.
   - **Profiles:** the admin creates profiles. Devices choose and switch profiles Netflix-style.
   - **Roles:** the admin role belongs to the device.
   - **Trust:** security between profiles relies on trust; an optional PIN (0.8) only locks the interface.
7. **Theme independence.**
   - **Engine:** the engine uses a neutral glossary.
   - **Themes:** each theme is a package in `src/themes/`. A CI check (`lint:theme-leak`) keeps theme vocabulary out of everything else.
   - **Stored data:** collectibles store a `slot` and a `tier`, never a themed name.
8. **Language.**
   - **Repository:** every artefact is in English.
   - **Interface:** text is European Portuguese and lives only in locale files (`src/i18n/` and each theme's `theme.json`).
9. **Release identity.** Each release is one minor version (`0.1`, `0.2`, ...), developed on its own `release/0.x` branch. It has no parallel numbering, and partial deliveries are patches. The plan is in `ROADMAP.md`.
10. **Licence.** MIT, chosen by the product owner when the repository was created.

## Consequences

- Some invariants cannot be enforced by the Firestore rules, because the rules cannot count documents or verify random draws:
  - the daily task limit;
  - the party size;
  - the opening day;
  - the reward tier draw.

  These are enforced in the client and covered by domain tests. Their integrity relies on trust within the family.
- Because there are no transactions, two devices acting on the same item at the same time resolve by rejection: the second batch fails as a whole, and the client must re-sync its view.
- Every Firestore rule needs emulator tests. The emulator needs Java, so CI runs them on every push; running them locally is optional.
- Without Cloud Functions there is no server-side scheduling. Recurring tasks are generated by clients when the app opens.
